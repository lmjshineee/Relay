# Relay 工程与评测规范

状态：待实现规范。MUST 为发布门槛；SHOULD 可通过有理由的设计记录调整。系统正确性要求与实验效果结论分开验收。

### 1. 不可破坏的工程约束

| 编号 | 等级 | 规则 |
|---|---|---|
| R01 | MUST | 所有工具副作用发生前，已有持久动作意图 |
| R02 | MUST | 同一 action ID 参数不可变；重复提交不擅自创建新执行 |
| R03 | MUST | UNKNOWN 不自动当作 FAILED；未知 shell 不盲目重试 |
| R04 | MUST | 单工作区单写者；回滚或重建前确认旧执行已停止 |
| R05 | MUST | 预算账本与审计历史不能随回滚、resume 重置 |
| R06 | MUST | SUCCEEDED 只由独立验收通过产生 |
| R07 | MUST | 缺失用量和缓存数据用 null/unknown 表示，不填零 |
| R08 | MUST | 输入仓库、控制面数据、隐藏验收和密钥不暴露为沙箱可写内容 |
| R09 | MUST | 检查点只有在 manifest 和所有工件持久化校验后才能发布 |
| R10 | MUST | 每个结论可追溯至固定配置、任务清单和原始运行记录 |
| R11 | SHOULD | 核心逻辑使用注入的时钟、模型与执行接口，便于故障测试 |
| R12 | SHOULD | 修改持久格式、恢复语义或评分规则时附 ADR 与迁移说明 |

仓库文本、模型输出、工具日志均属于数据，不可改变宿主权限、预算或评分规则。拒绝超出 schema 的工具参数，工具路径经规范化后仍需检查工作区边界及符号链接。容器对本项目提供执行隔离，但本地 Docker MVP 不宣称具备恶意多租户服务级隔离能力。

### 2. 编码与日志

公共边界使用明确类型与版本化模型；状态转换集中实现，不散落修改字符串。异常分类至少覆盖 configuration、provider_transient、provider_permanent、execution_timeout、workspace_conflict、artifact_corrupt、budget_exhausted、verification_failed、infrastructure_error。

禁止捕获所有异常后返回成功，禁止无上限重试，禁止用日志文本驱动状态机。进程启动优先 argv；只有用户工具确需 shell 时才进入显式 shell 接口，且仍在沙箱内执行。

输出流采用持续读取和磁盘/大小限制；模型可见截断与完整工件存储分开。达到总磁盘配额时停止动作并记录 `output_limit`，不得声称保存了完整日志。工件读取限制范围与大小，拒绝读取控制面文件。

日志默认包含 run/action/attempt/call ID、generation、事件序号、结构化原因和耗时。密钥不进入请求日志；对导出的文本做凭据检查。可追溯性不要求公开完整源码和私密轨迹，公开报告应使用脱敏且允许分享的 fixture。

### 3. 测试分层

1. 单元测试覆盖状态转换、预算算术、消息合法性、hash 核对和指标分母。
2. 集成测试使用真实 SQLite、本地文件系统和 Docker，验证跨模块边界。
3. 故障测试在子进程中实际终止 Controller/Worker，验证持久化窗口。
4. 端到端测试用脚本模型跑完整修复与独立验收；真实提供商另做显式 smoke test。

用例要验证业务不变量和失败行为，不仅断言内部函数被调用。对每个 MUST 至少有自动化用例或可复现检查证据；文档文字本身不是测试通过。

### 4. 必须覆盖的故障矩阵

| ID | 注入位置或故障 | 期望结果 |
|---|---|---|
| F01 | PLANNED 提交前崩溃 | 没有已执行副作用；恢复不发明动作 |
| F02 | PLANNED 后、Worker 接收前 | 重新提交相同 ID，不重复意图 |
| F03 | Worker 登记后、实际启动前 | 能核对未启动，或保守 UNKNOWN；不出现双启动 |
| F04 | 工具运行中 Controller 死亡 | Worker 独立继续；resume 接回状态 |
| F05 | 文件替换后、最终回执前死亡 | after_hash 成立则 RECONCILED，不再次追加 |
| F06 | shell 改文件后、最终回执前死亡 | UNKNOWN/BLOCKED，或按显式策略停止旧进程后回滚 |
| F07 | 最终回执后、数据库导入前死亡 | 导入已有回执，执行次数不增加 |
| F08 | Controller 导入事务中死亡 | 事件与状态全有或全无，无半更新 |
| F09 | checkpoint blob/manifest/提交之间死亡 | 半成品不可恢复；可用最后完整检查点 |
| F10 | checkpoint 后丢失容器 | 重建声明范围内状态；新 generation 拒绝旧回执 |
| F11 | 双 Controller 同时 resume | 只有一个获得 run 所有权 |
| F12 | 模型限流、超时、响应丢失 | 有界重试；未知计费保留；不执行部分工具调用 |
| F13 | 预算、步数、活动时间耗尽 | 不再调度；状态原因明确；resume 不清零 |
| F14 | 超量输出和超时子进程 | 无死锁；输出限制可见；进程树被清理或标记未知 |
| F15 | 摘要失败、上下文超限 | 不丢原始事件；消息合法；回退或明确暂停 |
| F16 | 工件损坏、磁盘写满 | 不发布虚假成功；引用校验失败阻塞恢复 |
| F17 | 快照含新建、删除、忽略文件 | 声明覆盖范围内状态逐项一致 |
| F18 | agent 修改公开测试或伪造成功日志 | 独立隐藏验收仍决定最终结果 |
| F19 | 取消与完成回执竞态 | 已完成动作可保留，但不新调度；最终 run 状态一致 |
| F20 | 回滚后再次运行并产生费用 | 原费用与新费用均保留，无重复计账或费用丢失 |

关键持久化窗口至少重复执行多次，并记录次数、注入位置和随机种子；次数在测试计划中固定。没有触达指定注入点的任务记作 `not_injected`，不能算作恢复成功。

### 5. 任务集与实验协议

先使用约 10 个开发任务调试；稳定后冻结 30–50 个评测任务作为目标规模，实际规模取决于预算和可运行性。开发集与评测集尽量不重叠。可从公开基准选择任务，但必须保留许可证、来源、固定 ID 和筛选理由；未运行完整基准不能声称完整榜单成绩。

冻结清单包括 task ID、repo/commit、镜像 digest、平台、CPU/内存、超时、验收版本、预算、故障计划及排除规则。正式结果出现后不因某种策略表现差而移除任务；环境失败保留并单列。

| 组别 | 恢复能力 | 上下文策略 |
|---|---|---|
| A | 无续跑；故障后按协议从基线重启 | append |
| B | 启用恢复 | append |
| C | 无续跑；故障后按协议从基线重启 | threshold |
| D | 启用恢复 | threshold |

另在同一恢复设置下比较 append、periodic、threshold。A/C 仍保留基础可观测日志、资源约束和预算，禁用的是恢复能力。故障后的从头重启费用计入同一实验 trial 总预算，不获得额外免费额度。

故障实验与无故障实验分别运行。相同任务使用同一注入位置，避免按墙钟随机杀进程造成条件不可比。各策略随机化执行顺序，记录重复编号与请求时间，降低服务负载变化的影响；模型 seed 即便可设置也不等于确定性。

三策略比较测量的是策略组合效果。若要声称收益来自日志外置、稳定前缀或阈值摘要中的某一项，还需要逐项开关的补充消融。不要用一组组合策略的结果替单项机制归因。

### 6. 指标定义与统计

| 指标 | 口径 |
|---|---|
| 总体任务成功率 | 独立验收 passed 数 / 冻结计划中的全部 trial 数；未运行与基础设施失败另列 |
| 有效执行成功率 | passed / 实际进入有效任务执行的 trial；必须同时报告总体口径 |
| 每成功任务费用 | 全部 trial 的累计费用 / passed 数，包含失败、重启、摘要；零成功时为 undefined |
| 恢复后任务成功率 | 注入且恢复后 passed 数 / 实际成功注入的 trial 数 |
| 恢复协议正确率 | 按规范续跑、核对或安全阻塞的数量 / 实际注入数量；安全阻塞不算任务修复成功 |
| 重复副作用 | 独立计数器/文件状态检测的非预期重复次数，不以“没抛异常”判断 |
| 重做工作量 | 依据动作血缘标注重复的调用、动作和耗时；不凭文本相似度猜测 |
| 延迟 | 排队、环境准备、模型、工具、恢复、验收、总墙钟；异步重叠阶段不机械相加 |
| TTFT | 客户端发请求至首个有效输出 token；排除连接事件；未流式观测则 null |
| 缓存用量 | 提供商/服务端明确返回的 cached token 或对应指标；不从延迟反推 |

费用有未知项时，报告已知值、保守上界、未知调用数及覆盖率；不能把不完整金额当作精确费用降低百分比。缓存输入可能是总输入的子集，计费适配器必须防止重复计数。

报告同时给出原始数量、每任务配对差值、重复次数与波动；样本不足时不声称显著提升。成功率下降时不能只强调费用降低。小样本下展示原始延迟分布，不将不稳定的 p99 当可靠结论。

### 7. 报告与证据规范

每份实验报告必须包含：研究问题、预先固定的配置、任务选择规则、全部结果清单、失败分类、费用完整性、对照方法、限制和原始数据引用。保存 harness commit、依赖锁 hash、prompt/策略版本、模型标识、镜像、资源及开始时间。

建议结果文件采用版本化 JSON/JSONL，字段包含 suite_id、trial_id、run_ids、task_id、group、repeat、fault_id、injected、final_status、cost_known、cost_upper_bound、unknown_calls、timings、artifact_refs。指标计算从这些记录和账本生成，避免在表格里手改数字。

简历陈述格式：在固定 N 个任务、K 类故障、R 次重复中，观察到某指标由 X 变化到 Y，同时报告成功率变化；附报告和代码版本。没有真实数据前只描述已实现机制，不填占位数字冒充结果。

### 8. 完成定义与代码审查

一个功能完成需同时满足：契约已实现、错误路径可解释、必要测试通过、日志和产物可定位、文档同步。仅正常路径演示通过不算恢复功能完成。

审查顺序：副作用边界 → 持久化窗口 → 并发与取消 → 预算 → 验收隔离 → 可观测性 → 可读性。涉及持久化的 PR 必须说明“在哪些提交窗口会崩溃，重启后怎样判断”。涉及优化的 PR 必须说明基线、资源条件与效果证据。

MVP 发布门槛：M1 闭环可复现；F01–F20 有执行结果和边界说明；未解决的正确性缺陷不得隐藏；离线演示可重复；至少一个真实模型案例；评测原始记录可重算。完成这些门槛仍不等于已经获得性能优势。
